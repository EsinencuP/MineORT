Теги: [ЗАКРЕПЛЕНО] / [ПРЕДЛАГАЕТСЯ] / [ПРОВЕРИТЬ] / [ОПРЕДЕЛИТЬ] / [РИСК] — как в аудите; [ПРЕДЛОЖЕНИЕ КОМАНДЫ] — термин, ключ или правило, которых нет в аудите.

Связанные файлы: [анализ аудита](01-audit-analysis.md) · [открытые решения](03-open-decisions.md) · [модель статусов](../01-product/02-user-status-model.md) · [роли и права](../01-product/03-roles-permissions.md) · [модель данных](../03-architecture/03-data-model.md).

## 2. Статусы (канонические значения)

Полные определения, переходы и инварианты — в [модели статусов](../01-product/02-user-status-model.md). Здесь — только значения, одинаковые во всех файлах пакета.

| Измерение | Ключ | Допустимые значения |
|---|---|---|
| Статус аккаунта | `users.account_status` | `active` · `suspended` · `banned` · `deleted` |
| Привязка ника | `minecraft_identities.binding_status` | `reserved` · `confirmed` · `released` |
| Тип аккаунта | `minecraft_identities.account_type` | `premium` · `offline` · `unknown` |
| Заявка | `applications.status` | `draft` · `pending` · `approved` · `rejected` · `withdrawn` |
| Приглашение | `invitations.status` | `active` · `exhausted` · `expired` · `revoked` |
| Участие в сообществе | `access_memberships.status` | `pending` · `approved` · `suspended` · `revoked` |
| Whitelist | `whitelist_entries.desired` / `applied_state` | desired: `on` · `off`; applied_state: `not_requested` · `pending` · `applied` · `failed` · `drift` |
| Игровая личность | `game_identity` | `unconfirmed` · `confirmed` |
| Действие Bridge | `server_actions.status` | `queued` · `leased` · `succeeded` · `failed_retryable` · `failed` · `expired` · `cancelled` |
| Вызов игрового входа | `login_challenges.status` | `pending` · `confirmed` · `denied` · `expired` · `abandoned` |
| Сервер Bridge | `bridge_servers.status` | `online` · `offline` · `paused` |
| Стадия онбординга (производная) | `onboarding_stage` | `guest` · `needs_rules` · `needs_nick` · `needs_access` · `application_pending` · `application_rejected` · `access_preparing` · `ready_to_install` · `first_login_pending` · `active` · `restricted` |
| Уровень доступа к платформе | — | `guest` · `tg_user` · `applicant` · `member` · `restricted` |
| Запрос (заказ) | `requests.status`, `type = order` | `open` → `in_progress` → `done` \| `cancelled` |
| Запрос (помощь) | `requests.status`, `type = help` | `seeking` → `volunteers_found` → `done` → `closed` |
| Видимость | `visibility` | `public` · `guild` · `private` |
| Статус модерации | `moderation_status` | `draft` · `pending` · `approved` · `hidden` |

Соответствие терминов UI статусам заказа/помощи (аудит стр. 363, 373): «Открыт» = `open`, «Взяли в работу» = `in_progress`, «Выполнен» = `done`, «Отменён» = `cancelled`; «Ищу помощь» = `seeking`, «Есть добровольцы» = `volunteers_found`, «Выполнено» = `done`, «Закрыто» = `closed`.

## 3. Роли и ранги

| Термин UI | Ключ в коде | Синонимы в аудите (запрещены в UI) | Определение |
|---|---|---|---|
| Игрок | `site_role = player` | Участник сайта | Базовая глобальная роль; уровень доступа определяется отдельно (стр. 526). |
| Модератор | `site_role = moderator` | — | Модерация заявок и контента по выданным разрешениям (стр. 526); назначается владельцем (OD-28). |
| Администратор | `site_role = admin` | Глобальный администратор (стр. 634) | Создаёт гильдии, назначает глав, управляет общими настройками (стр. 525). |
| Владелец (проекта) | `site_role = admin` + разрешение `roles.manage` | Владелец сервера, владелец MineOrt (стр. 467, 617) | Не отдельная роль, а admin с правом `roles.manage` (C-04). Не путать с главой гильдии и с Minecraft OP. |
| Глава | `guild_rank = owner` (уровень 1) | Owner, командир, президент (стр. 467, 511) | Руководитель **только своей** гильдии. Ровно один на гильдию. **Не** Minecraft OP (стр. 505). |
| Заместитель | `guild_rank = vice_leader` (2) | Вице-президент (стр. 511) | Управление людьми в пределах делегированных прав. |
| Первый / второй / третий помощник | `guild_rank = officer_1` / `officer_2` / `officer_3` (3–5) | Офицеры (стр. 1213) | Ранги с ограниченными организационными правами. |
| Участник | `guild_rank = member` (6) | Member | Участие без управленческих полномочий. |
| Гость | `guest` | Посетитель | Уровень доступа: не вошёл. |
| Пользователь Telegram | `tg_user` | — | Уровень доступа: вошёл через Telegram, допуск не подан. |
| Кандидат | `applicant` | Заявитель | Уровень доступа: подана заявка или применено приглашение, допуск не одобрен. В публичном каталоге не виден (AC-19). |
| Одобренный участник | `member` | Участник сообщества | Уровень доступа: `access_memberships.status = approved`. |
| Ограничен | `restricted` | Заблокированный (стр. 816) | Уровень доступа: `suspended`, `banned` или отозванный допуск. Перекрывает остальные стадии. |

Три измерения прав независимы: уровень доступа к платформе, `site_role`, `guild_rank` (аудит стр. 814–820). Ни один ранг гильдии не даёт OP, RCON, `site_role` или доступ к чужой гильдии (стр. 532, 829). Матрицы — в [ролях и правах](../01-product/03-roles-permissions.md).

## 4. Технические термины

| Термин | Определение |
|---|---|
| MineOrt Bridge (Bridge) | Собственный Java Paper-плагин: whitelist, игровая авторизация, события, метки; работает только с белым списком действий и только исходящим HTTPS (аудит стр. 677, 693). Подробнее — [протокол Bridge](../03-architecture/02-bridge-protocol.md). |
| `server_action` | Запись очереди команд backend → Minecraft с UUID `action_id` (`whitelist.add`, `whitelist.remove`, `player.kick`, `auth.release`, `marker.ack`, `tag.sync`) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; в аудите — «действие с UUID» (стр. 718). |
| `server_event` | Дедуплицированное игровое событие Minecraft → backend (первый вход, `marker.create_requested`); уникально по `(server_id, event_id)` [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Reconciliation (сверка) | Сопоставление реального whitelist на сервере с желаемым состоянием в БД: при старте и периодически; лишние записи — только `drift` для админа, без автоудаления [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; требование сверки — стр. 725. |
| Drift | `applied_state = drift`: фактическое состояние whitelist расходится с желаемым. |
| Limbo | Состояние игрока на сервере до игровой авторизации: заморозка, нет команд, чата и взаимодействий, инвентарь скрыт [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; соответствует принципу «до аутентификации не двигаться и не пользоваться вещами» (стр. 232). |
| Fail-closed | При недоступности backend или auth-сервиса новая игровая сессия не пускается в мир (OD-46, AC-30). |
| Step-up | Повторное подтверждение критичной админ-операции (TOTP или passkey) поверх Telegram-входа (стр. 635–636); срок окна — [ПРЕДЛОЖЕНИЕ КОМАНДЫ] (см. [NFR](../03-architecture/04-nfr-security.md)). |
| Offline-mode | `online-mode=false` на Paper: сервер не проверяет аккаунт через Mojang, поэтому «ник + whitelist» не доказывает личность (стр. 230). |
| Premium-игрок | Владелец лицензионного аккаунта; на offline-сервере получает автологин только при проверке сессии Mojang плагином [ПРОВЕРИТЬ] (C-14). |
| Offline-UUID / premium-UUID | UUID игрока на offline-сервере (производный от ника) и UUID Mojang. Смена ника меняет offline-UUID (стр. 967, OD-37). |
| `game_identity` | Подтверждена ли связь Telegram-профиля с игровым ником: `unconfirmed` · `confirmed`. |
| Игровой код | 6-значный код первого входа, TTL 5 минут [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; подтверждается в кабинете под Telegram-сессией. |
| OIDC (Telegram Login) | OpenID Connect-вход через Telegram (стр. 207) [ПРОВЕРИТЬ]; идентичность — Telegram ID, `@username` — изменяемое поле. |
| `.mrpack` | Формат пакета сборки Modrinth; основной формат MineOrt Client вместе с fallback `.zip` (стр. 268, OD-25). |
| BlueMap / Dynmap | Кандидаты движка карты (стр. 410–412); выбор — OD-16. |
| Paper | Серверное ядро Minecraft; версия — OD-22. |
| LuckPerms | Плагин прав; в аудите — возможный источник префиксов тегов гильдий (стр. 572); не форматирует чат сам. |
| AuthMe | Плагин игровой авторизации с паролями — вариант схемы входа (стр. 696, OD-23) [ПРОВЕРИТЬ]. |
| RLS | Row Level Security Postgres/Supabase (стр. 807); обязательно при выборе Supabase. |
| IDOR | Доступ к чужому объекту подстановкой идентификатора; негативные тесты в [роли и права](../01-product/03-roles-permissions.md). |
| Soft-delete | Логическое удаление с последующим физическим удалением медиа через 30 дней (OD-40). |
| Last-owner guard | Ограничение: нельзя удалить или понизить последнего главу гильдии (стр. 771, AC-23). |
| Feature flag (фича-флаг) | Переключатель, скрывающий волну P1 при провале go/no-go [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Карантин ника | Срок после перехода привязки в `released` (`quarantine_until`, по умолчанию 90 дней), в который ник нельзя занять никому, кроме прежнего владельца (reinstate) и admin со step-up; данные под offline-UUID не сбрасываются при освобождении, а архивируются действием Bridge `player.data_archive` только при фактической повторной выдаче ника другому пользователю (отложенная архивация); карантин и архив — только для ника с игровой историей ([протокол Bridge, п. 6.9](../03-architecture/02-bridge-protocol.md#69-карантин-ника-и-отложенная-архивация-данных-b1-major-4-minor-11-minor-1-sc-acc-11-sc-acc-12)) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Сверка числа (number matching) | Подтверждение входа в боте: limbo показывает двузначное число, бот предлагает выбрать верное из трёх и «Это не я»; **один выбор на challenge**: верное число — `confirmed`, неверное или «Это не я» — `denied`, кнопки гаснут ([протокол Bridge, п. 6.3](../03-architecture/02-bridge-protocol.md#63-последующие-входы)); защищает от подтверждения «вслепую» [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Источник входа | Признак подключения для блокировки перебора по паре «ник + источник» (единое правило: 5 неудач за 10 мин → блок пары на 15 мин; для игрового пароля дополнительно бюджет на ник — 20 неверных паролей в час отключают только парольный путь; [протокол Bridge, п. 6.5](../03-architecture/02-bridge-protocol.md#65-лимиты-и-блокировки-единое-правило-r3-10--minor-4)); рабочее определение — хэш с солью от IP, огрублённого до подсети; окончательно — [ОПРЕДЕЛИТЬ → OD-23]. |
| Режим восстановления БД | Процедура после восстановления из бэкапа: сайт в режиме обслуживания (только чтение), глобальный отзыв всех сессий и смена секрета сессий, внешний append-only журнал `audit_log` и `security_events` (RPO ≤ 5 мин), diff по этому журналу с повторным применением, Bridge на паузе (`paused`, `/auth/join` отказывает), возобновление только после закрытого diff ([протокол Bridge, п. 5.1](../03-architecture/02-bridge-protocol.md#51-режим-восстановления-бд-m11-r3-03--major-3)) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Challenge (вызов входа) | Запись `login_challenges` на одно подключение в limbo; живёт столько же, сколько limbo-соединение: при выходе или кике Bridge вызывает `POST /auth/challenges/{id}/abandon` и challenge становится `abandoned` ([протокол Bridge, п. 6.10](../03-architecture/02-bridge-protocol.md#610-жизненный-цикл-challenge-r3-01-r3-02)) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| `player.data_migrate` / `player.data_restore` | Действия Bridge: перенос данных игрока со старого UUID на новый при смене ника ([протокол Bridge, п. 6.7](../03-architecture/02-bridge-protocol.md#67-смена-ника-и-uuid-od-37-r3-05--major-5)) и возврат данных из архива при reinstate ([п. 6.9](../03-architecture/02-bridge-protocol.md#69-карантин-ника-и-отложенная-архивация-данных-b1-major-4-minor-11-minor-1-sc-acc-11-sc-acc-12)) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Tombstone удаления (`deletion_tombstones`) | Метка удалённого аккаунта: HMAC-хэш Telegram ID, `banned`, `ban_until`; для забаненного хранится не меньше срока бана и проверяется при Telegram-входе до создания `users`, чтобы бан не обходился удалением и повторной регистрацией [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| Публичные представления | `public_members`, `public_profiles`, `public_guilds`: единственный путь публичного чтения для `anon` и `authenticated`; прямого `SELECT` на базовые таблицы с закрытыми колонками нет ([модель данных, п. 6.1](../03-architecture/03-data-model.md#61-чтение-только-через-представления-r3-07--major-7)) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]. |
| PAPER-T | Тестовый Paper-сервер (стенд): та же версия и конфигурация плагинов, что и продовые, seed игроков и мира; локально или второй слот хостинга (US-E00-08, [архитектура, п. 7](../03-architecture/01-architecture.md#7-окружения-секреты-тестовый-paper)) |
| SP-NN | Спайк: прототип или замер до M1/M2 (SP-01…SP-08; SP-07 — замер скорости, кода нет; SP-08 — стек серверных плагинов и плагин приватов); код входит в историю-хозяина, часы спайков в сумму не добавляются |

## 7. Замечания для сведения

- В аудите «Social» используется как название раздела (стр. 97); в пакете в UI — «Общение», в коде — `social` (C-11).
- «Участник» в аудите встречается в трёх значениях (участник сообщества, участник гильдии `member`, участник события); в пакете: «одобренный участник» = `member` (уровень доступа), «участник гильдии» = `guild_rank = member`, «записавшийся» — для событий.
- Расшифровка «Доступ готов» зависит от OD-03; определение в таблице 1 даёт безопасный вариант по умолчанию [ПРЕДЛОЖЕНИЕ КОМАНДЫ].
