## 1. Цели и границы

### 1.1. Цели

1. Telegram-first вход без пароля: профиль MineOrt с устойчивым `user_id`, независимым от изменяемого `@username` (аудит стр. 197–207; AC-01, AC-25) [ЗАКРЕПЛЕНО].
2. Безопасные серверные сессии с отзывом; отдельная короткая админская сессия и step-up для критичных операций (аудит стр. 836–837; AC-34).
3. Согласие на сообщения бота (шаг «подключить бота») и согласие с политикой данных — без них обязательные уведомления и подтверждение игрового входа ботом недоступны (аудит стр. 207; G-06, OD-41, OD-45).
4. Восстановление доступа при потере Telegram через администратора (аудит стр. 970, 1080; G-02, OD-31).

### 1.2. Входит

| Пункт | Основание | SC |
|---|---|---|

## 2. Акторы и разрешения

| Актор | Что может в рамках TZ-02 |
|---|---|
| `guest` | Начать вход; открыть форму «Не могу войти в Telegram»; читать `/privacy` |
| `tg_user` и выше | Выйти; отозвать другие сессии; подключить бота; посмотреть свои привязки |
| `restricted` | Войти и увидеть только экран ограничения; выйти |
| `moderator` | Не имеет прав на перепривязку и восстановление (если не выдано разрешение) |
| `admin` (с разрешением `players.rebind`) | Подтвердить восстановление и перепривязку — **только со step-up** (AC-34) |
| Бот | Отправка уведомлений, обработка `/start` с одноразовым токеном привязки |

Права — [роли и права](../01-product/03-roles-permissions.md); проверка на сервере на каждом запросе, права читаются из БД (NFR-SEC-06). Выдача и изъятие прав `site_role` — только `admin` с `roles.manage` и step-up.

## 4. Состояния и UI

### 4.1. Состояния

| Измерение | Значения | Переходы (в рамках ТЗ) |
|---|---|---|
| `users.account_status` | active \| suspended \| banned \| deleted | `telegram_login` (создание → active); `suspend` / `ban` отзывают сессии (I-09); `delete` — SC-DSH-04: сессии отзываются, привязка Telegram рвётся сразу, ник уходит в карантин (данные не сбрасываются); самоудаление при `banned` / `suspended` запрещено (`ERR_DELETE_FORBIDDEN_BANNED`, удалить может только admin со step-up); хранение хэша Telegram ID — ОТКРЫТО → OD-40 / OD-45 [ОПРЕДЕЛИТЬ] |
| Сессия (`user_sessions`) | активна \| отозвана \| истекла (производные от `revoked_at`, `expires_at`) [ПРЕДЛОЖЕНИЕ КОМАНДЫ] | Выход, «отозвать все», бан, истечение, смена привязки Telegram |
| `telegram_identities.dm_consent` | true \| false | `bot.linked`, `bot.unlinked`, ошибка доставки (SC-AUTH-07 A2) |
| Уровень доступа | guest → tg_user | после успешного OIDC; далее — по [модели статусов](../01-product/02-user-status-model.md) |

Диаграммы и инварианты — в модели статусов (§3.6, I-03, I-09). Шаг «подключить бота» не вводит новой стадии `onboarding_stage`, это пункт чек-листа; жёсткость гейта — ОТКРЫТО → OD-41.

### 4.2. Экраны и маршруты

| Маршрут | Назначение | Состояния |
|---|---|---|
| `/login` | Вход через Telegram; ссылка «Не могу войти в Telegram» | loading «Проверяем вход…»; error «Не удалось войти через Telegram. Попробуйте ещё раз»; success — переход на шаг правил |

### 5.2. Эндпоинты (уровень контракта; детали — при реализации) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]

| Эндпоинт | Назначение | Ошибки / замечания |
|---|---|---|
| `GET /auth/telegram/start` | Создать `state`, `nonce`, PKCE; редирект к Telegram | `state` одноразовый, TTL 10 мин (NFR-SEC-07); 429 при превышении NFR-LIM-01 |
| `GET /auth/telegram/callback` | Проверка `state`, обмен кода, подпись ID token, `aud`/`iss`/`exp`, `nonce`; проверка `deletion_tombstones` (запись с `banned = true` и неистёкшим `ban_until` → отказ, `users` не создаётся); создание или нахождение `users`; создание сессии | Отмена, replay, невалидная подпись → отказ без раскрытия деталей; забаненный по tombstone — сообщение «Аккаунт заблокирован» и контакт, без создания аккаунта |
| `POST /auth/logout`, `POST /auth/sessions/revoke-all` | Выход, отзыв всех сессий | CSRF-защита (NFR-SEC-08) |
| `POST /bot/link-token`, webhook бота | Одноразовый токен привязки (deep link), привязан к `user_id` | Чужой/просроченный/использованный токен → «Ссылка устарела» |
| `POST /auth/step-up` | Подтверждение TOTP или passkey, действует 15 мин | Выбор TOTP vs passkey — ОТКРЫТО → OD-35 (G-18); по умолчанию TOTP [ПРЕДЛОЖЕНИЕ КОМАНДЫ] |
| `POST /recovery/request` | Форма «Не могу войти в Telegram»; одинаковый ответ | Лимит частоты — ОТКРЫТО → OD-31 (число) |
| `POST /admin/players/{id}/rebind` | Перепривязка Telegram | step-up обязателен; отзыв сессий; запись истории |

Telegram OIDC-клиент, домен и redirect URI у BotFather — [ПРОВЕРИТЬ] (R-17); проверка на staging в SP-01 до 19.11.

**Запасной контракт: классический Telegram Login Widget** [ПРЕДЛОЖЕНИЕ КОМАНДЫ; формат полей и алгоритм подписи — [ПРОВЕРИТЬ] по документации Telegram]. Применяется только если SP-01 покажет, что OIDC недоступен или не выдаёт нужных данных (R-17); основной контракт — OIDC выше.

| Шаг | Правило |
|---|---|
| Данные виджета | Виджет подключается в режиме JS-колбэка (`data-onauth`), а не `data-auth-url`: колбэк получает объект с полями `id`, `first_name`, `last_name`, `username`, `photo_url`, `auth_date`, `hash` и отправляет их на `POST /auth/telegram/widget-callback` (тело JSON; не GET-редирект, чтобы данные не попадали в URL, журналы и `Referer`); идентичность — только `id` (Telegram ID) [R3-18, MINOR-13] |
| Проверка подписи | `data_check_string` — все поля, кроме `hash`, в виде `key=value`, отсортированные по ключу, через перевод строки; `secret_key = SHA256(bot_token)`; `hash` должен равняться `hex(HMAC-SHA256(data_check_string, secret_key))`; сравнение за постоянное время |
| Свежесть | `auth_date` не старше 5 минут и не из будущего [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; иначе отказ |
| Replay | Пара `(telegram_id, auth_date, hash)` запоминается на срок свежести; повтор — отказ и `security_events` (`login_bad_signature` или `login_state_invalid`) |
| CSRF | У виджета нет `state`/`nonce`: `POST /auth/telegram/widget-callback` обязан нести CSRF-токен pre-auth сессии (заголовок `X-CSRF-Token`, выдаётся при открытии страницы входа, одноразовый или на время pre-auth сессии, сверяется с сессией на сервере); запрос без токена, с чужим или просроченным токеном — отказ 403 и `security_events` (`login_state_invalid`) до проверки подписи. Проверка `Origin` как основной механизм не используется (NFR-SEC-08: токен CSRF), `SameSite=Lax` — дополнительный рубеж [R3-18, MINOR-13] |
| Секрет | `bot_token` — только в менеджере секретов (NFR-SEC-10), не в клиенте и не в репозитории |

Остальное (создание `users`/`telegram_identities`, сессия, лимит 10 в минуту, проверка статуса `banned` до сессии) — как для OIDC; TC-AUTH-04a…c прогоняются для обоих контрактов.

### 5.3. События

Аудит: `user.created`, `bot.linked`, `bot.unlinked`, `recovery.requested`, `recovery.approved`, `recovery.cancelled`, перепривязка. Безопасность: `login_bad_signature`, `login_state_invalid`, `rate_limited`, `permission_denied`. Перечень окончательно фиксируется в ТЗ при реализации [ПРЕДЛОЖЕНИЕ КОМАНДЫ].

## 6. Безопасность и приватность

| Угроза | Контроль | TC |
|---|---|---|
| Replay и подмена ответа OIDC | `state` привязан к pre-auth сессии, `nonce`, PKCE, проверка подписи и `aud`/`iss`/`exp` | TC-AUTH-04a, 04b, 04c |
| CSRF на изменяющих запросах | Токен CSRF (NFR-SEC-08); `SameSite=Lax` — дополнительный рубеж | TC-AUTH-08a, 08b |
| Кража сессии, злоупотребление админской сессией | httpOnly/Secure/SameSite=Lax; админская сессия 12 ч без скольжения; step-up 15 мин; отзыв | TC-AUTH-02a…c, TC-ADM-02a…c |
| Работающая сессия после бана | Отзыв всех сессий; проверка прав из БД | TC-AUTH-06a, 06b |
| Захват аккаунта через восстановление | Только через admin со step-up; задержка 72 ч; уведомление старому владельцу «Это не я»; одинаковый ответ формы (нет перечисления ников) | TC-AUTH-05a, 05b, TC-ADM-06a |
| Перебор / спам форм | NFR-LIM-01; лимит формы восстановления — ОТКРЫТО → OD-31 | TC-AUTH-01b |
| Подмена привязки Telegram | Один Telegram на профиль (политика), `telegram_id` UNIQUE; история привязок | TC-ADM-06a…c |
| SQLi | Параметризованные запросы | TC-OPS-08a |
| Утечка персональных данных | Telegram ID, IP и коды не публикуются (аудит стр. 487, 804); RLS (NFR-SEC-06); выгрузка (SC-DSH-05) содержит только данные запросившего | TC-OPS-06a…f, TC-DSH-05a |
| Смена своей роли или статуса прямой записью клиентской ролью (T-PRIV-WRITE) | Клиентские роли не пишут в `site_role`, `account_status`, `binding_status` и др.; запись через backend/RPC `SECURITY DEFINER`, `GRANT` по колонкам (NFR-SEC-15) | TC-OPS-06g |
| Возврат удалённого аккаунта через повторный вход | Привязка Telegram разорвана сразу; повторный вход создаёт новый аккаунт без старых данных; ник — в карантине | TC-DSH-04c, TC-ACC-12d |
| Обход бана удалением аккаунта и повторной регистрацией (R3-06) | Самоудаление при `banned` / `suspended` запрещено (`ERR_DELETE_FORBIDDEN_BANNED`); tombstone с `banned` и `ban_until` проверяется при Telegram-входе до создания `users`, вход отклоняется | TC-DSH-04d |
| Чтение закрытых колонок `users`, `telegram_identities` напрямую (R3-07) | `anon` и `authenticated` не имеют `SELECT` на базовые таблицы; публичные поля — через представление `public_profiles` ([модель данных, п. 6.1](../03-architecture/03-data-model.md#61-чтение-только-через-представления-r3-07--major-7)) | TC-OPS-06h |
| Воскресшие сессии и роли после восстановления БД (R3-03) | Глобальный отзыв всех `user_sessions`, смена секрета сессий, сайт в read-only до закрытия diff, перепривязки Telegram и роли сверяются с внешним журналом | TC-OPS-01c |

Приватность: что хранится (Telegram ID, username, `dm_consent`, IP в `security_events`), сроки (IP 30 дней, `security_events` 180 дней, `user_sessions` до `expires_at` + 7 дней, NFR-OPS-02, 03) — [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; политика обработки и возраст — ОТКРЫТО → OD-45; удаление аккаунта и повторная регистрация того же Telegram — SC-DSH-04: привязка рвётся сразу, повторный вход создаёт новый аккаунт (TC-DSH-04c); хранение HMAC-хэша Telegram ID на 30 дней (для забаненного — не меньше срока бана, поля `banned` и `ban_until`) — ОТКРЫТО → OD-45 / OD-40 [ОПРЕДЕЛИТЬ] (G-09); несовершеннолетние — ветка OD-45 (самодекларация возраста, согласие родителя, минимизация данных); юрисдикция хранения Supabase/Vercel — [ПРОВЕРИТЬ].

## 7. Ограничения и ошибки

### 7.1. Числа

| Параметр | Значение | NFR |
|---|---|---|
| Попытки Telegram-входа | 10 в минуту на IP | NFR-LIM-01 |
| Свежесть `auth_date` (запасной контракт виджета) | ≤ 5 мин | [ПРЕДЛОЖЕНИЕ КОМАНДЫ] |
| Выгрузка своих данных | 1 в 24 ч, ссылка 24 ч | NFR-LIM-20 |
| TTL `state` | 10 мин, одноразовый | NFR-SEC-07 |
| Обычная сессия | 30 дней, скользящая | NFR-SEC-02 |
| Админская сессия | 12 ч, без скольжения | NFR-SEC-03 |
| Step-up | 15 мин | NFR-SEC-04 |
| Задержка восстановления | 72 ч | OD-31 (по умолчанию) |
| Чтение / запись p95 | < 500 мс / < 1 с | NFR-PERF-02, 03 |

### 7.2. Ошибки и деградация

| Ситуация | Поведение |
|---|---|
| `state`/`nonce`/подпись неверны, `state` просрочен | Вход отклонён, `security_events`; сообщение без технических деталей (SC-AUTH-04) |
| Лимит 10 в минуту | 429 «Слишком много попыток. Попробуйте через минуту» |
| Telegram недоступен | Вход новых пользователей недоступен; активные сессии работают (NFR-REL-10); сообщение как в SC-ONB-01 E1 |
| Нет Telegram `@username` | Профиль создаётся с отображаемым именем; работа не зависит от username (SC-AUTH-01 A2) |
| Бот не может писать | `dm_consent=false`; баннер в кабинете; обязательные уведомления дублируются на сайте; подтверждение входа переключается на резерв (SC-AUTH-07) |
| Telegram-ID удалённого пользователя | Привязка разорвана сразу, повторный вход — новый аккаунт; хэш — 30 дней; для забаненного вход отклоняется по tombstone на срок бана [ОПРЕДЕЛИТЬ → OD-45 / OD-40] |
| Недоступна БД/backend при входе | Вход отклонён; сообщение об ошибке (fail-closed для сессий) [ПРЕДЛОЖЕНИЕ КОМАНДЫ] |
