## 1. Цели и границы

### 1.1. Цели

1. Управляемый допуск: игрок попадает на сервер по приглашению (выдаёт `admin`, OD-36) или по заявке с решением модератора/админа (аудит стр. 209–213: два пути допуска описаны, но «кто может приглашать и сколько» в аудите — [ОПРЕДЕЛИТЬ]) [ПРЕДЛОЖЕНИЕ КОМАНДЫ, OD-36].
2. Согласие с правилами — предусловие допуска: версионируемые правила, повторное принятие при новой мажорной версии (G-04, C-18, AC-07, AC-33) [ПРЕДЛОЖЕНИЕ КОМАНДЫ].
3. Честные статусы: решение сайта (`desired`) отделено от факта применения (`applied_state`); «Доступ готов» — только при `applied` (AC-21, AC-28) (аудит §6.3, стр. 217–226; C-02).
4. Все решения — в аудит; посторонний не воспроизводит решение (AC-22).

## 2. Акторы и разрешения

| Актор | Действия |
|---|---|
| `guest` | Читать `/rules`, `/privacy`, предпросмотр `/invite/:code` (без погашения) |
| `tg_user` | Принять правила; выбрать ник; погасить приглашение; подать заявку; отозвать заявку |
| `applicant` | Видеть статус; отозвать заявку |
| `member` | Видеть статус допуска; видеть баннер об обновлении правил |
| `restricted` | Только экран ограничения |
| `moderator` (разрешение `applications.review`) | Очередь заявок: одобрить / отклонить с причиной; приостановка (по разрешению) |
| `admin` | Приглашения (выпуск, отзыв); публикация правил (`rules.publish`); бан/разбан (`players.ban`, step-up); смена ника (step-up); восстановление/отзыв допуска |
| Система | Создание `access_memberships`, `whitelist_entries`, `server_actions` |

Все проверки — на сервере (AC-33 проверяется прямым API, не только в UI). Матрица — [роли и права](../01-product/03-roles-permissions.md). Критичные операции (бан, разбан, смена ника/UUID, перепривязка) — со step-up (AC-34).

## 4. Состояния и UI

### 4.1. Состояния (канон; диаграммы — [модель статусов](../01-product/02-user-status-model.md))

| Измерение | Значения | Ключевые переходы |
|---|---|---|
| `applications.status` | draft \| pending \| approved \| rejected \| withdrawn | `submit`, `approve`, `reject` (причина обязательна), `withdraw` / `discard` |
| `invitations.status` | active \| exhausted \| expired \| revoked | `issue`, `redeem`, `ttl_elapsed`, `revoke` |
| `access_memberships.status` | pending \| approved \| suspended \| revoked | `approve`, `deny`, `suspend`, `restore`, `revoke`, `reapply` |
| `whitelist_entries` | `desired` on \| off; `applied_state` not_requested \| pending \| applied \| failed \| drift | `desired_changed` — здесь; `bridge_succeeded`, `retries_exhausted`, `reconcile_mismatch` — TZ-04 |
| `minecraft_identities.binding_status` | reserved \| confirmed \| released | `reserved` при выборе ника; `released` при отзыве, бане, удалении аккаунта, смене ника (перепривязка Telegram ник не освобождает) — с `quarantine_until` (по умолчанию 90 дней [ПРЕДЛОЖЕНИЕ КОМАНДЫ]) только для ника с игровой историей (когда-либо `applied` или `game_identity = confirmed`; резерв без игровой истории освобождается сразу): ник в карантине занять нельзя, кроме прежнего владельца (reinstate с нетронутыми данными, OD-48) и admin со step-up; выдача ника другому пользователю требует `player_data_archives.status = archived` для последней `released`-записи |
| `users.account_status` | active \| suspended \| banned \| deleted | `suspend`/`ban` — каскад отзыва допуска |
| `onboarding_stage` | guest … restricted (11 значений) | вычисляется; `needs_rules` → `needs_nick` → `needs_access` → `application_pending` / `access_preparing` → `ready_to_install` |

Инварианты: I-01 («Доступ готов» только при `desired=on` и `applied`), I-02 (эквивалентность: `desired=on` ⇔ `approved` ∧ `active` ∧ ник не `released`; следствие — `suspended`/`revoked` ⇒ `desired=off` и `whitelist.remove`), I-05 (один ник — один Telegram), I-06 (одна `pending`-заявка), I-07 (без правил нельзя подать заявку и погасить приглашение), I-12 (карантин: ник не выдаётся другому пользователю до `quarantine_until` и пока нет архива `archived`).

Приглашение выдаёт только `admin` (OD-36) ⇒ погашение сразу даёт `membership.approved` без модерации [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; при смене OD-36 потребуется промежуточный `membership.pending`.

## 5. API и данные

### 5.1. Сущности ([модель данных](../03-architecture/03-data-model.md))

| Сущность | Ключевые ограничения |
|---|---|
| `rules_versions` | UNIQUE (`version_major`, `version_minor`); версии неизменяемы; одна актуальная |
| `rules_acceptances` | UNIQUE (`user_id`, `rules_version_id`) |
| `minecraft_identities` | partial UNIQUE `lower(nickname)` для `reserved` и `confirmed` (I-05) |
| `invitations` | `token_hash` — SHA-256, токен 128 бит; `used_count <= max_uses`; TTL 7 дней |
| `invitation_redemptions` | UNIQUE (`invitation_id`, `user_id`); атомарное увеличение `used_count` |
| `applications` | partial UNIQUE (`user_id`) WHERE `status='pending'`; пауза 7 дней — в приложении |
| `access_memberships` | partial UNIQUE (`user_id`) для `pending`/`approved`/`suspended`; `revoke_reason` |
| `whitelist_entries` | UNIQUE `minecraft_identity_id`; триггер: `suspended` ⇒ `desired=off` |
| `server_actions` | создаётся при `desired_changed` (`whitelist.add` / `whitelist.remove`); исполнение — TZ-04 |
| `audit_log`, `security_events`, `notification_deliveries` | аудит решений; события безопасности; доставка уведомлений |

**Паттерн записи (B2, NFR-SEC-15).** Привилегированные колонки этого ТЗ — `applications.status`, `decided_by`, `decided_at`, `access_memberships.status`, `invitations.status`, `used_count`, `whitelist_entries.*`, `minecraft_identities.binding_status`, `quarantine_until`, `users.account_status` — клиентские роли напрямую не пишут: все переходы выполняет backend или RPC `SECURITY DEFINER` с проверкой прав, инвариантов и записью в `audit_log`. Где запись с клиента разрешена (поля черновика заявки, текст отзыва), права выданы `GRANT UPDATE` по колонкам. В матрице RLS вместо «З» для таких таблиц — «через API» ([модель данных, п. 8.1](../03-architecture/03-data-model.md#81-паттерн-записи-b2)); проверка — TC-OPS-06g (прямой PATCH/INSERT под клиентской ролью отклоняется).

### 5.2. Эндпоинты (уровень контракта) [ПРЕДЛОЖЕНИЕ КОМАНДЫ]

| Эндпоинт | Назначение | Ошибки |
|---|---|---|
| `GET /rules`, `GET /rules/history` | Публичные версии правил | — |
| `POST /rules/accept` | Принять актуальную мажорную версию | 409 `rules.outdated` при гонке с публикацией |
| `POST /minecraft/nickname` | Резервирование ника | 422 формат; 409 занят |
| `GET /invite/{code}` | Предпросмотр без погашения; сохраняет контекст в pre-auth cookie (срок — [ПРЕДЛОЖЕНИЕ КОМАНДЫ], в сценарии принят 1 час) | причины: истекло / исчерпано / отозвано |
| `POST /invitations/redeem` | Погашение: требует вход, принятые правила, ник | 403 без правил (AC-33); 409 исчерпано |
| `POST /applications`, `POST /applications/{id}/withdraw` | Подача, отзыв | 409 вторая `pending` или пауза; 403/404 для чужой заявки (IDOR) |
| `POST /admin/applications/{id}/decision` | `approve` / `reject` (причина обязательна) | 409 при повторном решении; 403 для постороннего |
| `POST /admin/invitations`, `POST /admin/invitations/{id}/revoke` | Выпуск, отзыв | только `admin` |
| `POST /admin/rules` | Публикация версии | 403 для moderator (TC-ADM-03a) |
| `POST /admin/players/{id}/suspend`, `.../restore`, `.../ban`, `.../unban`, `.../nickname` | Приостановка, восстановление, бан, разбан, смена ника | step-up обязателен для бана, разбана, смены ника |

Одобрение выполняется **в одной транзакции**: решение + `membership.approved` + `whitelist_entries(desired=on, applied_state=pending)` + `server_actions.queued` + `audit_log` (атомарность — [ПРЕДЛОЖЕНИЕ КОМАНДЫ]).

### 5.3. События

Аудит: `application.submitted`, `application.approved`, `application.rejected`, `application.withdrawn`, `invitation.issued`, `invitation.redeemed`, `invitation.revoked`, `invitation.expired`, `membership.created`, `membership.approved`, `membership.denied`, `membership.suspended`, `membership.restored`, `membership.revoked`, `membership.reapplied`, `whitelist.requested`, `whitelist.retried`, `rules.published`, `rules.accepted`, `identity.nickname_reserved`, `identity.nickname_released`, `user.banned`, `user.unbanned`, `stepup.passed`. Безопасность: `permission_denied`. Перечень — [модель статусов, §10](../01-product/02-user-status-model.md) [ПРЕДЛОЖЕНИЕ КОМАНДЫ].

## 6. Безопасность и приватность

| Угроза | Контроль | TC |
|---|---|---|
| Обход правил через прямой API (AC-33) | Сервер отклоняет `submit`/`redeem` без принятия актуальной мажорной версии | TC-ONB-03a, TC-ACC-02a, 05a |
| IDOR на заявки, приглашения, ник | Проверка владельца; 404/403 без раскрытия данных | TC-ACC-05b |
| Перебор/раскрытие приглашений | Токен 128 бит, хранится SHA-256; предпросмотр без погашения; одинаково бедные ответы | TC-ACC-02b, 03a…c, TC-ADM-08a…d |
| Повторное применение приглашения / гонка | Атомарное `used_count`, UNIQUE (`invitation_id`, `user_id`) | TC-ACC-02a, 02b |
| Захват ника, два Telegram на один ник | partial UNIQUE по `lower(nickname)`; ответ без раскрытия владельца | TC-ACC-12a…c, TC-ACC-01c |
| Повторное занятие освобождённого ника и наследование данных прежнего игрока (T-IMPERSONATION) | Карантин `quarantine_until` (90 дней по умолчанию, только для ника с игровой историей); данные не сбрасываются при бане, отзыве и удалении; `player.data_archive` ставится при повторной выдаче ника, а выдача на любом пути (обычный, админский досрочный со step-up, фоновая задача окончания карантина) отклоняется с `nick.archive_required`, пока нет архива `archived` (проверка в RPC и триггере БД; `nick_issue_blocked_no_archive` — алерт); занять раньше может только прежний владелец (reinstate) или admin со step-up | TC-ACC-11d, TC-ACC-12c, TC-ACC-12d |
| Смена статуса заявки, членства, приглашения прямой записью клиентской ролью (T-PRIV-WRITE) | Запись только через backend/RPC; `GRANT` по колонкам | TC-OPS-06g |
| Решение постороннего / повторное решение | Права на сервере; решение один раз (409); аудит | TC-ADM-01a…d |
| Ложный «Доступ готов» | `applied_state=applied` — единственное условие; при `failed`/`drift` показ «задержка» | TC-ACC-07a…c, 08a…c, TC-DSH-01a…c |
| Эскалация прав через отзыв/бан | Критичные операции со step-up; moderator без прав на бан и смену ника | TC-ADM-05a…c, TC-ADM-02a…c |
| XSS в тексте правил и заявок | Санитизация markdown; экранирование при выводе | TC-ADM-03*, TC-OPS-08a |
| Утечка внутренних заметок модератора | Заметка не отдаётся публичным и пользовательским API | TC-ACC-06a |

Приватность: Telegram ID, IP, коды и журналы не публичны (аудит стр. 487, 804); причина отклонения видна только заявителю; внутренняя заметка — только модераторам/админам. Сроки хранения заявок и аудита — OD-40 (по умолчанию: soft-delete, аудит хранится) и [NFR](../03-architecture/04-nfr-security.md) (`audit_log` 1 год). Согласие на обработку данных — OD-45.

## 7. Ограничения и ошибки

### 7.1. Числа

| Параметр | Значение | NFR / источник |
|---|---|---|
| `pending`-заявок на пользователя | 1 | NFR-LIM-02; I-06 |
| Повтор заявки после отклонения | через 7 дней | NFR-LIM-02 [ПРЕДЛОЖЕНИЕ КОМАНДЫ] |
| Приглашение | TTL 7 дней, одноразовое (`max_uses=1`), токен 128 бит, хранится SHA-256 | NFR-LIM-03 |
| Формат ника | 3–16 символов, латиница, цифры, `_`, без учёта регистра [ПРОВЕРИТЬ правила ника Java Edition] | [Bridge, §1](../03-architecture/02-bridge-protocol.md) |
| Реакция на заявку | ≤ 48 ч | OD-28 (по умолчанию) |
| Применение whitelist p95 (сервер онлайн) | < 60 с | NFR-PERF-04 |
| Лимиты формы заявки | длины полей — ОТКРЫТО → OD-28 | — |

### 7.2. Ошибки и деградация

| Ситуация | Поведение |
|---|---|
| Вторая `pending`-заявка / двойной клик | 409, существует одна |
| Подача раньше паузы | 409 «Новую заявку можно подать после <дата>» |
| Правила не приняты (обход UI) | 403/422, запись не создаётся |
| Приглашение недействительно | Понятная причина: «истекло» / «исчерпано» / «отозвано» |
| Одобрение при выключенном Minecraft | `membership.approved`, `desired=on`, `applied_state=pending`; UI «Идёт подготовка доступа»; после старта сервера Bridge применяет (AC-21) |
| `failed` или `drift` | UI «задержка»; админ видит в `/admin/bridge`; «Доступ готов» не показывается |
| Решение по заявке, уже не `pending` | 409, аудит без дубля |
| Бан последнего `admin` с `roles.manage` или самобан | Запрещено [ПРЕДЛОЖЕНИЕ КОМАНДЫ] |
| Выдача ника, для которого нет архива `archived` или архив `failed` | 409 `nick.archive_required` и постановка `player.data_archive`; при `failed` — отказ даже админу, `security_events` `nick_issue_blocked_no_archive`, алерт (R3-04) |
| Самоудаление забаненного или приостановленного | `ERR_DELETE_FORBIDDEN_BANNED`: удалить такой аккаунт может только admin со step-up; повторный Telegram-вход после админ-удаления забаненного отклоняется по tombstone (TC-DSH-04d) |
| Telegram не может доставить уведомление | Решение и статус видны в кабинете; доставка не влияет на статус (SC-AUTH-07 A3) |
