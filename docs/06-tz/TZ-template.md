# MineOrt IV — шаблон технического задания (TZ-template)

**Статус:** черновик для утверждения · **Базовая дата:** 13.11.2026 (пятница) · **Запуск:** 10.12.2026 (четверг), 27 календарных дней.

Шаблон основан на рекомендованном порядке аудита (аудит §25, стр. 1102: цели и границы → акторы и разрешения → пользовательские сценарии → состояния и UI → API/данные → безопасность и приватность → ограничения/ошибки → критерии приёмки → тесты → зависимости → отложенные функции). Раздел 0 (паспорт) и раздел 12 (журнал изменений) добавлены командой [ПРЕДЛОЖЕНИЕ КОМАНДЫ].

Как пользоваться:

1. Скопируйте структуру ниже в новый файл `TZ-NN-<slug>.md` (имена ASCII, содержимое на русском, UTF-8).
2. Заполните **все** разделы 0–12. Пустой раздел не удаляется: пишется «Не применимо» с причиной.
3. Любое неизвестное оформляется строкой `ОТКРЫТО → OD-xx` со ссылкой на [реестр открытых решений](../00-analysis/03-open-decisions.md). Голое «TBD» запрещено; если подходящего OD нет, он заводится в реестре.
4. Числа, правила, механизмы и даты, которых нет в аудите, помечаются [ПРЕДЛОЖЕНИЕ КОМАНДЫ]; решения владельца — [РЕШЕНИЕ ВЛАДЕЛЬЦА ДД.ММ.ГГГГ]; остальные теги — как в аудите: [ЗАКРЕПЛЕНО] / [ПРЕДЛАГАЕТСЯ] / [ПРОВЕРИТЬ] / [ОПРЕДЕЛИТЬ] / [РИСК].
5. Ссылки только относительные. Содержимое не дублируется: протокол, модель данных, NFR, сценарии и тесты — ссылками на файлы пакета.
6. Ссылки на аудит: `(аудит §6.3, стр. 217–226)` — номера строк файла аудита.

## Структура ТЗ

### 0. Паспорт

Что писать: идентификатор и название, версия, статус, владелец, даты, связанные эпики, OD, риски, релиз и волна.

| Поле | Значение |
|---|---|
| ID и название | `TZ-NN` · название по аудиту §25 (стр. 1085–1100) |
| Версия | `0.1` (черновик) · `1.0` (утверждено владельцем) |
| Статус | черновик / на ревью / утверждено / реализуется / принято |
| Владелец ТЗ | роль или имя; утверждает — владелец проекта |
| Релиз и волна | P0 / P1a / P1b / P1c / P2 (и веха M0–M5) |
| Эпики | E00–E19; истории US-Exx-NN из [бэклога](../04-plan/02-backlog.md) |
| Открытые решения | OD-xx, блокирующие это ТЗ, со сроком |
| Риски | R-xx из [реестра рисков](../04-plan/03-risk-register.md) |
| Связанные файлы | пакет документов, на которые опирается ТЗ |

### 1. Цели и границы

Что писать: зачем это ТЗ и что оно решает; что входит и что **не** входит (список «входит» / «не входит» по P0 / P1 / P2); привязка к решению владельца о границе релиза (OD-34); инварианты, которые нельзя нарушить.

Подсказки: каждый пункт «входит» должен иметь ссылку на SC или AC; каждый пункт «не входит» — причину и куда перенесён (раздел 11).

### 2. Акторы и разрешения

Что писать: акторы (гость, `tg_user`, `applicant`, `member`, `restricted`; `site_role`: player / moderator / admin; боты и системные актёры: Bridge, планировщик); матрица «действие × актор». Проверки прав — на сервере, не только в интерфейсе (аудит §16.2, стр. 822–829).

Подсказки: опирайтесь на [роли и права](../01-product/03-roles-permissions.md) и [модель статусов](../01-product/02-user-status-model.md); три измерения доступа не смешивать (аудит стр. 814–820); канонические перечисления брать только из пакета.

### 3. Сценарии

Что писать: перечень SC-<DOM>-NN, на которые опирается ТЗ (ссылки на файлы [сценариев](../02-scenarios/01-scenarios-access-p0.md)), с релизом и волной; для каждого — одна строка о роли в этом ТЗ. Сценарии здесь не переписываются.

Подсказки: негативные и краевые сценарии перечисляются отдельно (истёкшее приглашение, подмена ника, Minecraft выключен, fail-closed и т.п.).

### 4. Состояния и UI

Что писать: автоматы состояний (ссылки на разделы [модели статусов](../01-product/02-user-status-model.md)); маршруты и экраны ([IA](../01-product/01-information-architecture.md)); для каждого экрана — состояния loading / empty / error / success, ключевые тексты, доступность (NFR-A11Y).

Подсказки: макеты — вне объёма (TZ-01); здесь — поведение и тексты состояний; тексты правил сервера не придумываются (OD-06).

### 5. API и данные

Что писать: эндпоинты и их контракты (метод, путь, вход, выход, коды ошибок, идемпотентность); сущности [модели данных](../03-architecture/03-data-model.md) (поля, ограничения, индексы, RLS); события для `audit_log`, `server_actions`, `security_events`; фоновые задачи.

Подсказки: каждая сущность — ссылкой на 03-data-model; расхождения с моделью фиксируются в «Замечаниях» (раздел 12) и исправляются в исходном файле, не копируются.

### 6. Безопасность и приватность

Что писать: модель угроз для области ТЗ (угроза → контроль → TC; см. [NFR и безопасность](../03-architecture/04-nfr-security.md)); сессии и CSRF; лимиты и антиабьюз; какие данные собираются, кто их видит, срок хранения (OD-40, OD-45); обязательные негативные проверки.

Подсказки: любое действие, меняющее права или допуск, проверяется на сервере и пишется в аудит; admin-операции — со step-up (AC-34).

### 7. Ограничения и ошибки

Что писать: числовые лимиты (ссылки на NFR-LIM-NN), SLO (NFR-PERF-NN), таблица ошибок (код, HTTP, текст пользователю, поведение UI), поведение при недоступности зависимостей (Telegram, Bridge, Minecraft, backend).

Подсказки: честные статусы — никакого ложного успеха; «Доступ готов» только при `applied_state = applied`.

### 8. Критерии приёмки

Что писать: перечень AC-01…AC-34, которые закрывает ТЗ, с релизом и волной; дополнительные критерии области; связь с go/no-go ([план релиза, п. 4](../04-plan/01-release-plan.md#4-критерии-gono-go)).

Подсказки: каждый AC — минимум один TC; негативные критерии обязательны.

### 9. Тесты

Что писать: ссылки на TC в [приёмочных тестах](../05-qa/01-acceptance-tests.md), сгруппированные по сценариям, с уровнем (E2E Playwright / API / Plugin-интеграция на тестовом Paper / ручной) и приоритетом; тестовые данные и окружения; что проверять в БД и аудите.

Подсказки: ID TC закреплены в файле 05-qa и в реестре «SC → TC» сценариев; не перенумеровывать.

### 10. Зависимости

Что писать: от каких ТЗ, эпиков, OD, внешних сервисов и спайков зависит реализация; порядок работ; какие вехи (M0–M5) задают срок.

Подсказки: внешние зависимости (Telegram, BisectHosting, Supabase, Vercel) помечаются [ПРОВЕРИТЬ], пока интеграция не проверена на прототипе.

### 11. Отложено

Что писать: что осознанно не делается в этой версии (P2 и перенесённое по лестнице сокращений); условия возврата; ссылки на OD и эпики.

Подсказки: функции из «никогда не режем» сюда не попадают (offline-безопасность, честные статусы, бэкапы, аудит админ-действий, серверная проверка прав гильдий, приватность меток).

### 12. Журнал изменений

Что писать: таблица «дата · версия · автор · что изменилось · основание (решение, OD, замечание)»; подраздел «Замечания для сведения» — расхождения с другими файлами пакета и допущения.
