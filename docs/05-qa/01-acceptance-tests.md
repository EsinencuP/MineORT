## 1. Стратегия тестирования

### 1.1. Статус документа

**Приложения пока нет — тест-кейсы являются спецификацией.** Каждый TC описывает ожидаемое поведение будущей реализации на уровне «дано / когда / тогда»; кода тестов, фикстур и окружений на 13.11.2026 не существует. Реализация тестов — часть эпика E19 ([backlog](../04-plan/02-backlog.md)); ID тест-кейсов стабильны и не перенумеровываются (на них ссылаются сценарии, [роли и права](../01-product/03-roles-permissions.md), [протокол Bridge](../03-architecture/02-bridge-protocol.md), [модель данных](../03-architecture/03-data-model.md), [NFR](../03-architecture/04-nfr-security.md), [план релиза](../04-plan/01-release-plan.md)). Числа в тест-кейсах (лимиты, TTL, пороги) — из [NFR](../03-architecture/04-nfr-security.md) и [протокола Bridge](../03-architecture/02-bridge-protocol.md), все [ПРЕДЛОЖЕНИЕ КОМАНДЫ], пока их не утвердил владелец.

### 1.2. Уровни тестирования

| Уровень | Что проверяет | Инструмент (предлагается) | Где запускается |
|---|---|---|---|
| **E2E Playwright** | Пользовательские пути в браузере: CTA, вход, формы, статусы, UI-тексты, mobile 320 px и desktop, клавиатура | Playwright (проекты desktop и mobile) | staging |
| **API** | Серверные проверки прав, лимитов, гонок, статусов; **«обход UI»** — прямые HTTP-вызовы без интерфейса, прямые URL файлов, прямые обращения к REST/Realtime; RLS-матрица ролей `anon` / `authenticated` / owner / moderator / admin | Playwright `APIRequestContext` либо тест-раннер проекта + SQL-проверки состояния БД [ПРЕДЛОЖЕНИЕ КОМАНДЫ] | local, staging |
| **Плагин-интеграция на тестовом Paper** | Bridge: подписи HMAC и Ed25519, `whitelist.add/remove`, `player.kick`, reconciliation, limbo, игровой код, fail-closed, `/marker new` | Тестовый Paper-сервер с продовой конфигурацией плагинов; управляемый тестовый игровой клиент (бот-клиент) [ПРОВЕРИТЬ], управляемые часы backend | staging-стенд «PAPER-T» |
| **Ручной** | Проверки безопасности (pentest-lite, социальная инженерия на первом входе, premium/Mojang [ПРОВЕРИТЬ]), тест восстановления из бэкапа, ротация секретов, визуальная проверка UX, нагрузка | Чек-листы, [NFR](../03-architecture/04-nfr-security.md), runbook | staging / prod-like |

Приоритет автоматизации: Blocker и Critical — автоматизируются обязательно (кроме ручных по природе: TC-OPS-01b, TC-OPS-04e, TC-GUIDE-03c); Major — по возможности; Minor — допускается ручной прогон. Имена и порядок не зависят от уровня.

### 1.3. Приоритеты и критерии прохождения

| Приоритет | Смысл | Правило |
|---|---|---|
| **Blocker** | Провал блокирует релиз волны | 100 % пройдены до go/no-go своей волны |
| **Critical** | Обязателен до go/no-go волны | 100 % пройдены до go/no-go |
| **Major** | Обязателен до релиза | допускается отсрочка только решением владельца с записью в журнале M4 |
| **Minor** | Желателен | не блокирует |

Каждая волна проверяется отдельно ([release-plan §4.2](../04-plan/01-release-plan.md#42-волны-p1-и-фича-флаги)): провал жёстких критериев (AC-18, AC-23, AC-31) не компенсируется другими результатами — волна остаётся под фича-флагом.

### 1.4. Окружения и тестовые данные

| Окружение | Назначение | Условия |
|---|---|---|
| **local** | Разработка, API-тесты, RLS-тесты на локальной БД | Моки Telegram и Bridge [ПРЕДЛОЖЕНИЕ КОМАНДЫ] |
| **staging** | E2E, API, интеграция на PAPER-T, регрессия, нагрузка | Конфигурация равна продовой ([release-plan §4](../04-plan/01-release-plan.md#4-критерии-gono-go)); тестовый Telegram-бот и тестовые Telegram-аккаунты [ПРОВЕРИТЬ: настройка OIDC и домена у BotFather, R-17]; отдельные ключи Bridge и Ed25519; управляемые часы для проверки TTL и окон |
| **PAPER-T** | Тестовый Paper-сервер: версия MC/Paper/Java — по OD-22, плагины по продовому списку, offline-режим | Включается и выключается тестом (AC-21); изолирован от прода |
| **prod** | Только прогон smoke без записи (read-only), после запуска | Реальные данные не используются в тестах; тестовые учётные записи помечены |

Данные: сидирование фикстур скриптом перед прогоном; после прогона — сброс; приватные данные реальных людей не используются. Тексты правил — заглушка до 01.12 (OD-06).

### 1.5. Фикстуры (персоны и сущности)

Используются в Given-условиях тест-кейсов.

| Фикстура | Состояние |
|---|---|
| **F-GUEST** | Нет сессии; `site_role` не назначена |
| **F-TG** | Вошёл через Telegram, `onboarding_stage=needs_rules`, ника нет |
| **F-NICK** | `tg_user`, правила приняты, ник `reserved`, заявки/приглашения нет |
| **F-APPL** | Ник `reserved`, `applications.status=pending`, `membership=pending` |
| **F-MEM-NEW** | `member`: `membership=approved`, `desired=on`, `applied_state=applied`, `game_identity=unconfirmed` |
| **F-MEM** | `member`: как F-MEM-NEW, `game_identity=confirmed`, стадия `active` |
| **F-RESTR** | `restricted` (бан/приостановка) |
| **F-MOD** | `site_role=moderator` с нужным разрешением; **F-MOD0** — moderator без конкретного разрешения |
| **F-ADM** | `site_role=admin` с активным step-up (≤15 мин); **F-ADM0** — admin без step-up |
| **F-OWN-A / F-OWN-B** | `owner` гильдии A / B |
| **F-VICE-A, F-OFF-A, F-OFF-A2, F-MEMBER-A** | `vice_leader`, `officer_1`, `officer_2`, `member` гильдии A |
| **F-USER2** | Второй независимый `member` (для проверок «чужое», IDOR) |
| **BR-ON / BR-OFF** | Bridge online / Bridge остановлен (`bridge_servers.status=offline`, heartbeat отсутствует >90 с) |

«**Обход UI**» — вызов API/URL напрямую (curl/APIRequestContext) под тем же уровнем доступа, без интерфейса; ожидание — те же коды отказа, что и при проверке через UI.

### 1.6. Именование и структура

`TC-<DOM>-NN[a-z]`, где `NN` совпадает с номером сценария `SC-<DOM>-NN`; домены ONB, AUTH, ACC, GAME, GUIDE, SOC, POLL, EVT, REQ, GAL, MAP, MRK, PLR, GLD, DSH, ADM, OPS. Идентификатор вида `TC-ACC-02` без буквы — **группа** (все кейсы сценария SC-ACC-02; на группы ссылаются backlog и [модель данных](../03-architecture/03-data-model.md)). Каждый кейс: Уровень · Связи (SC, AC, NFR/прочее) · Приоритет · Релиз/волна, далее Given / When / Then / And («And» — проверки в БД, аудите и событиях). Канонические перечисления (`applied_state`, `onboarding_stage`, `server_actions.status` и т. д.) — как в [модели статусов](../01-product/02-user-status-model.md) и [плане пакета](../00-analysis/01-audit-analysis.md).

## 3. Тест-кейсы по доменам

Каждый кейс привязан к сценарию (колонка «Связи»). Блоки сгруппированы по сценариям; заголовок группы (`TC-<DOM>-NN`) — идентификатор группы.

### 3.1. P0 — Онбординг (ONB)

### TC-ONB-01 · Группа SC-ONB-01 «Гость нажимает «Начать играть»»

#### TC-ONB-01a · CTA гостя ведёт на `/login` с сохранением возврата
- **Уровень:** E2E Playwright · **Связи:** SC-ONB-01; AC-01; OD-44 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-GUEST открывает `/`.
- **When:** Нажимает «Начать играть».
- **Then:** Открывается `/login` с Telegram-входом; после успешного входа пользователь возвращается в онбординг (шаг по `onboarding_stage`), а не на главную.
- **And:** В БД до входа нет записей `users`; параметр возврата не содержит персональных данных.

#### TC-ONB-01b · CTA виден без прокрутки на 320 px
- **Уровень:** E2E Playwright (mobile) · **Связи:** SC-ONB-01; AC-01; NFR-A11Y, NFR-PERF-05 · **Приоритет:** Major · **Релиз:** P0
- **Given:** Вьюпорт 320×568, F-GUEST.
- **When:** Открывает `/`.
- **Then:** «Начать играть» виден в первом экране без горизонтальной прокрутки, клик по нему работает, фокус виден при навигации клавиатурой.
- **And:** LCP главной < 2,5 с в профиле mid-mobile 4G (NFR-PERF-05).

### TC-ONB-02 · Группа SC-ONB-02 «Авторизованный пользователь нажимает «Начать играть»»

#### TC-ONB-02a · CTA по каждой из 11 стадий (параметризованный)
- **Уровень:** E2E Playwright (параметризация по стадиям) · **Связи:** SC-ONB-02; AC-02; OD-03, OD-44 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** Пользователь с сессией в каждой из стадий: `guest`, `needs_rules`, `needs_nick`, `needs_access`, `application_pending`, `application_rejected`, `access_preparing`, `ready_to_install`, `first_login_pending`, `active`, `restricted`.
- **When:** Нажимает CTA на `/`.
- **Then:** Текст и цель соответствуют таблице [SC-ONB-02](../02-scenarios/01-scenarios-access-p0.md#sc-onb-02--авторизованный-пользователь-нажимает-начать-играть); Telegram-вход не запрашивается; адрес сервера и «Можно подключаться» скрыты для `application_pending`, `application_rejected`, `access_preparing`, `restricted`.
- **And:** `restricted` перекрывает остальные стадии; записей в `audit_log` нет.

#### TC-ONB-02b · Стадия пересчитывается при клике; повторный вход не запрашивается
- **Уровень:** E2E Playwright + API · **Связи:** SC-ONB-02; AC-02 · **Приоритет:** Major · **Релиз:** P0
- **Given:** Страница `/` отрисована для F-APPL; в другой вкладке заявку одобрили (стадия сменилась).
- **When:** Клик по устаревшему CTA «Заявка на рассмотрении».
- **Then:** Цель вычисляется на сервере заново (переход по актуальной стадии), UI не доверяется; при истёкшей сессии — «Сессия завершилась. Войдите снова» и `/login` с возвратом.
- **And:** Прямой переход на закрытый шаг (подача заявки при `needs_rules`) → 403/422 и редирект на актуальный шаг.

### TC-ONB-03 · Группа SC-ONB-03 «Принятие правил»

#### TC-ONB-03a · Подача заявки без принятия правил, обход UI
- **Уровень:** API · **Связи:** SC-ONB-03; AC-33 · **Приоритет:** Blocker · **Релиз:** P0
- **Given:** F-TG, `rules_acceptances` для актуальной мажорной версии нет.
- **When:** Прямой `POST` подачи заявки (минуя UI).
- **Then:** 403/422, заявка не создана.
- **And:** `applications` без новой записи; запись о попытке в `security_events` не обязательна (ожидаемая навигация, при повторах — по правилу сценария).

#### TC-ONB-03b · Принятие правил создаёт согласие на актуальную мажорную версию
- **Уровень:** E2E Playwright + API · **Связи:** SC-ONB-03; AC-07, AC-33; OD-06, OD-45 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-TG, опубликована версия правил v1.0.
- **When:** Принимает правила на шаге онбординга.
- **Then:** Создана запись `rules_acceptances` ровно на актуальную мажорную версию; стадия `needs_rules` → `needs_nick`.
- **And:** Повторное принятие идемпотентно (нет дубля); время и версия записаны.

#### TC-ONB-03c · Минорная правка не требует повтора, мажорная требует
- **Уровень:** API + E2E Playwright · **Связи:** SC-ONB-03, SC-ADM-03; AC-07, AC-33; OD-06 · **Приоритет:** Major · **Релиз:** P0
- **Given:** F-MEM (принял v1.0).
- **When:** Админ публикует v1.1 (минор), затем v2.0 (мажор).
- **Then:** После v1.1 повторное принятие не требуется; после v2.0 у F-TG-новичков стадия `needs_rules`, у уже одобренных F-MEM показан баннер, доступ не отзывается.
- **And:** Блокировка игрового входа при новой мажорной версии — открытый вопрос (OD-06), не проверяется.

### TC-ONB-04 · Группа SC-ONB-04 «Инвайт-ссылка до входа»

#### TC-ONB-04a · Просмотр ссылки не погашает приглашение; контекст сохраняется через вход
- **Уровень:** E2E Playwright · **Связи:** SC-ONB-04; AC-03, AC-26; OD-36; G-19 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-GUEST и активное приглашение `/invite/:code`.
- **When:** Открывает ссылку, входит через Telegram.
- **Then:** После входа он попадает на шаг приглашения с сохранённым контекстом; `invitations.status` остаётся `active` до явного погашения.
- **And:** В БД нет `invitation_redemptions` до подтверждения.

#### TC-ONB-04b · Контекст потерян — ручной ввод кода; лимит частоты `/invite/:code`
- **Уровень:** E2E Playwright + API · **Связи:** SC-ONB-04; AC-26; OD-36 · **Приоритет:** Major · **Релиз:** P0
- **Given:** Контекст приглашения утерян (другое устройство/истёк pre-auth контекст).
- **When:** Пользователь вводит код вручную; затем серия запросов `/invite/:code` с одного IP.
- **Then:** Ручной ввод работает; сверх лимита — 429, различий во времени ответа для несуществующих кодов нет.
- **And:** Токен в логах/URL-аналитике не раскрывается.

### 3.2. P0 — Аутентификация (AUTH)

### TC-AUTH-01 · Группа SC-AUTH-01 «Первый вход через Telegram»

#### TC-AUTH-01a · Первый вход создаёт пользователя, идентичность и сессию
- **Уровень:** E2E Playwright · **Связи:** SC-AUTH-01; AC-01; NFR-SEC-01, NFR-SEC-02, NFR-SEC-07 · **Приоритет:** Blocker · **Релиз:** P0
- **Given:** F-GUEST, новый тестовый Telegram-аккаунт.
- **When:** Проходит Telegram OIDC-вход.
- **Then:** Созданы `users` (`account_status=active`), `telegram_identities`, сессия (cookie httpOnly, Secure, SameSite=Lax, 30 дней rolling); устойчивый `user_id` не зависит от `@username`.
- **And:** Стадия `needs_rules`; пароль не запрашивается.

#### TC-AUTH-01b · Пользователь без `@username`; лимит 10 в минуту на IP
- **Уровень:** E2E Playwright + API · **Связи:** SC-AUTH-01; AC-01; NFR-LIM-01 · **Приоритет:** Major · **Релиз:** P0
- **Given:** Telegram-аккаунт без `@username`; отдельно — серия из 11 попыток входа с одного IP за минуту.
- **When:** Выполняет вход / серию попыток.
- **Then:** Вход без `@username` успешен (отображается имя); 11-я попытка → 429.
- **And:** Превышение лимита фиксируется (метрика/`security_events`), вход с другого IP не затронут.

### TC-AUTH-02 · Группа SC-AUTH-02 «Повторный вход, сессия, выход, отзыв»

#### TC-AUTH-02a · Повторный вход: тот же `user_id`, статусы неизменны
- **Уровень:** E2E Playwright · **Связи:** SC-AUTH-02; AC-02 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM вышел из системы.
- **When:** Входит снова через Telegram.
- **Then:** Тот же `user_id`, `onboarding_stage=active`, `membership`, `applied_state`, `game_identity` не изменились; CTA ведёт в «Как подключиться».
- **And:** Новая запись `user_sessions`; предыдущие — по политике.

#### TC-AUTH-02b · Выход отзывает сессию; после отзыва — 401
- **Уровень:** API + E2E Playwright · **Связи:** SC-AUTH-02; NFR-SEC-05 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM с активной сессией.
- **When:** Нажимает «Выйти»; затем повторяет запрос с прежним cookie.
- **Then:** Запись `user_sessions` отозвана, запрос → 401; «Выйти из всех устройств» отзывает остальные сессии.
- **And:** Отзыв мгновенный (без ожидания TTL).

#### TC-AUTH-02c · Сроки сессий: админская 12 ч без скольжения, обычная 30 дней rolling
- **Уровень:** API (управляемые часы) · **Связи:** SC-AUTH-02; NFR-SEC-02, NFR-SEC-03 · **Приоритет:** Major · **Релиз:** P0
- **Given:** F-ADM и F-MEM; часы стенда управляются.
- **When:** Сдвиг времени на 12 ч 1 мин с активностью админа; на 29 дней с активностью игрока.
- **Then:** Админская сессия истекла несмотря на активность; обычная продлена (скользящая).
- **And:** Cookie-атрибуты неизменны (NFR-SEC-01).

#### TC-AUTH-08a · CSRF: изменяющий запрос без токена/Origin отклоняется
- **Уровень:** API · **Связи:** SC-AUTH-02; NFR-SEC-08; T-CSRF · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM с сессией; сторонний Origin.
- **When:** `POST /logout` и любые изменяющие запросы от чужого Origin/без CSRF-токена.
- **Then:** Отклонены (403), состояние не изменилось.
- **And:** Запись в журнале ошибок безопасности.

#### TC-AUTH-08b · CSRF: изменение состояния только не-GET
- **Уровень:** API · **Связи:** SC-AUTH-02; NFR-SEC-08; T-CSRF · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM.
- **When:** Пытается выход/принятие правил/подачу заявки методом GET (или cross-site form).
- **Then:** Изменение не выполняется (405/403); SameSite=Lax не позволяет cross-site POST с cookie.
- **And:** Перечень изменяющих эндпоинтов проверен автоматически (нет GET-мутаций).

### TC-AUTH-03 · Группа SC-AUTH-03 «Смена Telegram @username»

#### TC-AUTH-03a · Смена `@username` не ломает профиль
- **Уровень:** E2E Playwright + API · **Связи:** SC-AUTH-03; AC-25 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM в гильдии (если P1b включена) со своей заявкой и историей; пользователь меняет `@username` в Telegram.
- **When:** Входит снова.
- **Then:** Тот же `user_id`; заявка, членство, whitelist, гильдия, история не изменились; отображаемое имя обновлено.
- **And:** Изменение записано в `telegram_identity_history`.

#### TC-AUTH-03b · Захват освободившегося `@old` другим человеком
- **Уровень:** E2E Playwright + API · **Связи:** SC-AUTH-03; AC-25 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** Пользователь A сменил `@old` на `@new`; новый человек B занял `@old`.
- **When:** B входит в MineOrt.
- **Then:** Создан новый `user_id` для B; доступа к профилю, заявке и членству A нет.
- **And:** Идентификация только по Telegram ID, не по `@username`.

### TC-AUTH-04 · Группа SC-AUTH-04 «Отмена входа, невалидная подпись, replay»

#### TC-AUTH-04a · Неверная подпись или replay Telegram — сессии нет
- **Уровень:** API · **Связи:** SC-AUTH-04; AC-01 (негатив); NFR-SEC-07; T-REPLAY-OIDC · **Приоритет:** Blocker · **Релиз:** P0
- **Given:** Подделанный ID token (неверная подпись) и ранее использованный валидный ответ.
- **When:** Отправляются на callback входа.
- **Then:** Сессия не создаётся, пользователь не создаётся.
- **And:** Запись в `security_events`; проверяются `aud`/`iss`/`exp`.

#### TC-AUTH-04b · Повторное использование `state`/`nonce`, чужая браузерная сессия, просроченный `state`
- **Уровень:** API · **Связи:** SC-AUTH-04; NFR-SEC-07; T-REPLAY-OIDC · **Приоритет:** Blocker · **Релиз:** P0
- **Given:** Начатый вход; `state` одноразовый с TTL 10 мин.
- **When:** (1) Повтор `state`; (2) callback из другой браузерной сессии; (3) callback после 10 мин.
- **Then:** Все три отклоняются без создания сессии.
- **And:** `security_events` фиксирует тип отказа.

#### TC-AUTH-04c · Отмена виджета Telegram
- **Уровень:** E2E Playwright · **Связи:** SC-AUTH-04; AC-01 · **Приоритет:** Major · **Релиз:** P0
- **Given:** F-GUEST на `/login`.
- **When:** Закрывает окно Telegram-входа/отказывает.
- **Then:** Возврат на `/login` с понятным сообщением; `users` не создан.
- **And:** Нет сессии и нет cookie.

### TC-AUTH-05 · Группа SC-AUTH-05 «Потеря доступа к Telegram»

#### TC-AUTH-05a · Запрос восстановления не раскрывает данные аккаунта
- **Уровень:** E2E Playwright + API · **Связи:** SC-AUTH-05; AC-34; OD-31; T-TG-LOSS · **Приоритет:** Critical · **Релиз:** P0

- **Уровень:** Plugin-интеграция на PAPER-T + API · **Связи:** SC-ACC-11, SC-ADM-05, SC-DSH-04, SC-ACC-12; AC-22, AC-05; I-12; T-IMPERSONATION · **Приоритет:** Blocker · **Релиз:** P0
- **Given:** F-MEM с ником N в offline-режиме (игровая история есть: `applied` и `confirmed`); у N в мире есть инвентарь, эндер-сундук, приват и права LuckPerms; BR-ON. Параметризованный прогон: (1) `revoke` членства админом, (2) бан со step-up, (3) удаление аккаунта (SC-DSH-04).
- **When:** Выполняется действие из Given; затем (а) данные N проверяются сразу после действия; (б) F-USER2 пытается занять N до `quarantine_until`; (в) админ со step-up досрочно выдаёт N пользователю F-USER2; (г) отдельный прогон: после бана выполняется `reinstate` (OD-48) в карантине; (д) гонка reinstate и архивации (R4-03): (д1) `player.data_archive` в `queued` (Bridge offline) → reinstate отменяет только это действие (архив `cancelled`), данные не тронуты; (д2) действие `leased` (Bridge выполняет) → reinstate отвечает `reinstate.archive_in_progress` (409) и ждёт финального статуса; (д3) действие уже отменено (`cancelled`), но Bridge вернул поздний `succeeded` → backend автоматически ставит `player.data_restore` (`restore_action_id`), данные возвращены; (е) бессрочный бан (`banned_until IS NULL`): `quarantine_until='infinity'`.

- **And:** `audit_log`: `player.data_archive` с результатом (только при повторной выдаче); при недоступном Bridge архивация остаётся `queued`, ник не выдаётся; ник без игровой истории (никогда `applied`, не `confirmed`) освобождается сразу без карантина и архивации (R3-08).

- **And:** `security_events: nick_quarantine_denied` для (1), `nick_issue_blocked_no_archive` для (4) и (5); записей `reserved` у F-USER2 нет.

### TC-GAME-07 · Группа SC-GAME-07 «Параллельный и повторный вход под тем же ником»

#### TC-GAME-07a · Второе подключение при `pending challenge` отклоняется; после выхода X владелец входит сразу
- **Уровень:** Plugin-интеграция на PAPER-T · **Связи:** SC-GAME-07, SC-GAME-01; AC-05, AC-29; T-IMPERSONATION · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM-NEW; владелец O подключён, в limbo, `login_challenges.status=pending`; атакующий X (другой источник) знает ник.
- **When:** Прогон 1: X подключается под тем же ником; затем O завершает подтверждение. Прогон 2 (R3-02): X подключился первым и висит в limbo с `pending challenge`, затем отключается; O подключается сразу после.
- **Then:** Прогон 1: подключение X отклонено (409 `ERR_LOGIN_IN_PROGRESS`, «Этот ник сейчас используется»); `challenge` O остаётся `pending`, TTL не сбрасывается; подтверждение O проходит, limbo снят. Прогон 2: при `player.quit` X Bridge вызвал `POST /auth/challenges/{id}/abandon`, `challenge` → `abandoned`; O входит сразу, без ожидания TTL, получает собственный новый `challenge`.
- **And:** `security_events: concurrent_join_denied` (ник, грубый источник X); владельцу в бот уходит нейтральное оповещение об отказе (в пределах 3 в час на ник; сообщение challenge владельца в этот лимит не входит, R4-01а); блокировка ERR_LOGIN_IN_PROGRESS действует только пока соединение живо.

#### TC-GAME-07b · Ник уже в сети и авторизован: второе подключение отклонено, владелец не выбит
- **Уровень:** Plugin-интеграция на PAPER-T · **Связи:** SC-GAME-07, SC-GAME-03; AC-05, AC-29; T-IMPERSONATION · **Приоритет:** Blocker · **Релиз:** P0
- **Given:** F-MEM авторизован и играет (инвентарь, позиция); X знает ник.
- **When:** X подключается под тем же ником (offline-клиент); попытка повторяется 5 раз; вариант — X с источника владельца.
- **Then:** Каждое подключение X отклонено на `AsyncPlayerPreLoginEvent` (локальная проверка Bridge и 409 `ERR_NICK_ALREADY_ONLINE` от `POST /auth/join`, без отдельного эндпоинта состояния ника, R3-14) до входа в мир; сессия владельца не прервана (нет `player.kick` владельца, позиция, инвентарь и состояние `game_identity` неизменны); X не получает ни одного игрового пакета мира.
- **And:** `security_events: concurrent_join_denied`; поведение ванильного Paper «кикнуть старого игрока» отключено; при недоступном backend проверка состояния ника fail-closed (вход X закрыт).

#### TC-GAME-07c · Блокировка перебора по паре «ник + источник»; владелец снимает только со сверкой числа; соседи не блокируются; challenge владельца не вытесняется спамом (R4-01)
- **Уровень:** API + Plugin-интеграция на PAPER-T + Telegram-бот (тестовый) · **Связи:** SC-GAME-07, SC-GAME-05; AC-05; NFR-LIM-16, NFR-LIM-21, NFR-LIM-22, NFR-LIM-23; T-BRUTE-GAME; R-8 · **Приоритет:** Critical · **Релиз:** P0
- **Given:** F-MEM; источник X (атакующий) и источник Y — другой игрок за тем же NAT, что и X, со своим ником; владелец O со своего источника, где он уже подтверждал вход (`last_confirmed_at` задан) и, отдельным прогоном, с нового источника, где вход не подтверждался; X ни разу не подтверждал вход под ником O; `dm_consent=true`.
- **When:** X делает 5 неудач за 10 минут под ником O; затем (1) O входит со своего источника; (2) Y входит под своим ником; (3) X пытается ещё раз; (4) O пытается снять блок кнопкой «Это я» без выбора числа; (5) O выбирает в боте верное число для заблокированной пары; (6) генерируется 5 оповещений об отказах владельцу за час; (7) **прогон R4-01г:** X делает 30 циклов «подключился–вышел» под ником O со своего источника (чужого, без подтверждённых входов), затем O входит в игру; (8) при исчерпанном лимите оповещений (6) O входит снова; неверные пароли с подтверждённого источника O не засчитываются в бюджет пароля (R4-01в).
- **Then:** Пара «ник O + источник X» заблокирована на 15 минут (423); (1) вход O не заблокирован; (2) Y входит нормально (общий NAT не блокирует соседей, блок по IP не применяется); (3) X получает 423; (4) блок не снят; (5) блокировка снимается досрочно только после верного числа, X при этом не получает доступа к игре без подтверждения; (6) в бот приходит не больше 3 оповещений об отказах в час на ник, остальные — дайджестом (R3-10); (7) в бот уходит не более 3 challenge от X за 10 минут (включая `abandoned`), 4-е и последующие подключения получают подписанный `denied` (`ERR_CHALLENGE_BUDGET`) без строки `login_challenges`, без сообщения в бот и без записи в дайджест; challenge владельца O приходит в бот сразу, число сверяется с первой попытки, O входит в игру (`confirmed`, `last_confirmed_at` обновлён); (8) сообщение challenge приходит владельцу независимо от лимита оповещений (не уходит в дайджест); источник с `last_confirmed_at` не подпадает под бюджет challenge, а его неверные пароли не увеличивают `password_credentials.budget_failures`.
- **And:** `security_events: game_auth_bruteforce` и `challenge_budget_exceeded` (одна запись на пару за окно); владельцу оповещение в бот (в пределах лимита об отказах); счётчик ведётся по паре, а не по сессии (ротация сессий блок не обходит); остаточный риск (угон источника владельца, срок исключения 30 дней) — R-8, [ПРОВЕРИТЬ].

- **Given:** На staging сделан бэкап БД; после него (в пределах последних суток) забанен F-MEM-A (бан, `whitelist.remove`, `player.kick` в журнале Bridge), отозван допуск F-MEM-B, понижена `site_role` F-MOD-C, перепривязан Telegram у F-MEM-D, отозвано приглашение I-1, отозвана сессия F-MEM-E; удалён аккаунт F-MEM-F (запись `deletion_tombstones`, хэш Telegram ID, R4-06); ник N1 выдан F-USER2 после карантина с выполненным архивом; админом сменён ник F-MEM-G (`player.data_migrate`); все события есть во внешнем append-only приёмнике `audit_log` и `security_events`; затем БД восстановлена из бэкапа, в котором эти состояния ещё прежние.

- **Then:** Пока diff не закрыт, сайт доступен только на чтение, старые сессии недействительны, вход в игру закрыт (`POST /auth/join` при `paused` отказывает, fail-closed), действия не выдаются; сверка не ставит `whitelist.add` ни для F-MEM-A, ни для F-MEM-B; баны, отзывы, понижение роли, перепривязка Telegram, отзыв приглашения и отзыв сессии повторно применены до снятия режима; удалённый аккаунт F-MEM-F снова стёрт (tombstone с хэшем сохранён), ник N1 не возвращён прежнему владельцу, архив N1 учтён (запись по `archive_id` из журнала Bridge), смена ника F-MEM-G сверена с применёнными `action_id` (R4-06); F-MEM-A и F-MEM-B после возобновления не получают доступа; случаи, которых нет во внешнем журнале, остаются в diff для ручного решения.
- **And:** `audit_log`: `ops.restore_mode_opened`, `ops.restore_mode_closed` (кто разобрал diff, сколько записей перенесено по категориям); оригинальный журнал во внешнем приёмнике не изменён; возобновление Bridge без step-up невозможно (TC-ADM-02a).

- **Уровень:** Plugin-интеграция на PAPER-T + API · **Связи:** SC-OPS-04, SC-GAME-02; AC-27, AC-29, AC-05; NFR-SEC-10, NFR-SEC-11; T-BRIDGE-SECRET, T-IMPERSONATION · **Приоритет:** Blocker · **Релиз:** P0

- **When:** (1) Прямой `SELECT` (REST и SQL) закрытых колонок и `SELECT *` базовых таблиц ролями `anon` и `authenticated`; (2) чтение через представления `public_members`, `public_profiles`, `public_guilds`; (3) чтение профиля F-MEM с включённой приватностью через `public_profiles`; (4) попытка прочитать закрытые колонки через представление (фильтры, `select=` с лишними полями, join на базовую таблицу).
- **Then:** (1) отказ на уровне БД (нет GRANT SELECT на базовые таблицы либо по колонкам); (2) возвращаются только публичные поля (ник, дата первого входа, гильдия и т. п., OD-29); (3) поля, скрытые `privacy_settings`, не возвращаются (фильтр внутри представления); (4) закрытых колонок нет, join на базовую таблицу отказывает; кандидаты и отклонённые заявители в представлениях отсутствуют (AC-19).
- **And:** Владелец представления задан явно (`security_invoker=false` с фильтром внутри либо GRANT по колонкам); на каждой базовой таблице представления есть явная политика `CREATE POLICY … TO view_owner USING (…)`, и представления под `anon` возвращают строки, а не пусто из-за RLS (R4-05); агрегаты `votes` для `anon` доступны только через RPC `poll_results`, прямой `SELECT` `votes` под `anon` отклоняется; результат сверяется с матрицей RLS (в ячейках «Ч*» базовых таблиц — «через представление»); `security_events` фиксирует отказы.

### 3.9. P1 — Общение: лента, новости, модерация (SOC)

Права на публикацию — OD-02, OD-27: гость видит официальные новости и public-галерею; `applicant` читает; `member` публикует посты и ивенты (с лимитами); новости — `moderator`+. Лимиты — NFR-LIM-04…LIM-12.

### TC-SOC-01 · Группа SC-SOC-01 «Пост со скриншотом»

#### TC-SOC-01a · `guest`, `tg_user`, `applicant` создают пост через API → 403
- **Уровень:** API · **Связи:** SC-SOC-01, SC-SOC-06; AC-08; OD-02 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** F-GUEST, F-TG, F-APPL.
- **When:** Прямой `POST` создания поста.
- **Then:** 401 (гость) / 403; пост не создан.
- **And:** `restricted` тоже получает 403.

#### TC-SOC-01b · Публикация поста с одним скриншотом: автор и медиа корректны
- **Уровень:** E2E Playwright · **Связи:** SC-SOC-01; AC-08; OD-27 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** F-MEM, изображение PNG ≤10 МБ.
- **When:** Создаёт пост с текстом и скриншотом.
- **Then:** Пост опубликован с корректным автором и вложенным изображением; в ленте он виден разрешённой аудитории хронологически.
- **And:** `posts`, `media`, `media_attachments` связаны; `site_activity` записывает действие.

#### TC-SOC-01c · Видимость `public` / `guild` / `private` для разных ролей
- **Уровень:** API (параметризованный) · **Связи:** SC-SOC-01; AC-08, AC-31 (смежно); NFR-SEC-13 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** Три поста: `public`, `guild`, `private`.
- **When:** Читают F-GUEST, F-APPL, F-MEM другой гильдии, член той же гильдии, автор, moderator.
- **Then:** Каждый видит только разрешённое; закрытое запрашивается — 404 (а не 403).
- **And:** Прямой URL изображения закрытого поста недоступен.

#### TC-SOC-01d · 11-е изображение в посте — отказ
- **Уровень:** API · **Связи:** SC-SOC-01; AC-08; NFR-LIM-12 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** F-MEM добавляет изображения к посту.
- **When:** Прикрепляет 11-е.
- **Then:** Отказ (422) с понятным сообщением; первые 10 сохранены.
- **And:** Квота хранилища не увеличена для отклонённого файла.

### TC-SOC-02 · Группа SC-SOC-02 «Официальная новость и закрепление»

#### TC-SOC-02a · Member публикует новость или закрепляет → 403
- **Уровень:** API · **Связи:** SC-SOC-02; OD-27 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** F-MEM.
- **When:** Публикует официальную новость / закрепляет.
- **Then:** 403; новость не создана.
- **And:** Попытка в `security_events: authz.denied`.

#### TC-SOC-02b · Модератор публикует и закрепляет; новость видна `guest`
- **Уровень:** E2E Playwright · **Связи:** SC-SOC-02; OD-02, OD-27 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** F-MOD с `news.publish`.
- **When:** Публикует новость и закрепляет.
- **Then:** Новость на главной и в ленте; гость её видит; закреплённая — сверху.
- **And:** `audit_log`: публикация и закрепление.

#### TC-SOC-02c · Снятие закрепа и правка пишутся в аудит
- **Уровень:** API · **Связи:** SC-SOC-02 · **Приоритет:** Minor · **Релиз:** P1a
- **Given:** Закреплённая новость.
- **When:** Модератор снимает закреп и правит текст.
- **Then:** Изменения применены; история правок сохранена.
- **And:** `audit_log` содержит актора и время.

#### TC-SOC-02d · Moderator без `news.publish` → 403
- **Уровень:** API · **Связи:** SC-SOC-02; OD-27 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** F-MOD0 без `news.publish`.
- **When:** Публикует новость.
- **Then:** 403.
- **And:** Разрешения читаются из БД, не из токена (NFR-SEC-06).

### TC-SOC-03 · Группа SC-SOC-03 «Жалоба и модерация»

#### TC-SOC-03a · Жалоба → решение модератора: скрыть / отклонить
- **Уровень:** E2E Playwright · **Связи:** SC-SOC-03; OD-28; T-SPAM · **Приоритет:** Major · **Релиз:** P1a
- **Given:** Опубликованный пост; F-USER2 жалуется; F-MOD с `content.moderate`.
- **When:** Модератор скрывает пост (в другом прогоне — отклоняет жалобу).
- **Then:** `moderation_status=hidden` либо жалоба закрыта; автор видит решение; жалоба ≤24 ч в очереди (OD-28).
- **And:** `audit_log`: решение и причина.

#### TC-SOC-03b · Moderator без `content.moderate` → 403
- **Уровень:** API · **Связи:** SC-SOC-03 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** F-MOD0.
- **When:** Решает жалобу.
- **Then:** 403.
- **And:** Очередь модерации недоступна.

#### TC-SOC-03c · Повторная жалоба — 409; жалоба на свой материал — 422
- **Уровень:** API · **Связи:** SC-SOC-03 · **Приоритет:** Minor · **Релиз:** P1a
- **Given:** Жалоба F-USER2 на пост подана.
- **When:** Повторная жалоба от него; автор жалуется на свой пост.
- **Then:** 409 и 422 соответственно.
- **And:** Дубль жалобы не создан.

#### TC-SOC-03d · Скрытый материал недоступен по API и прямому URL → 404
- **Уровень:** API · **Связи:** SC-SOC-03, SC-ADM-07 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** Пост скрыт модератором.
- **When:** Запрашивается по API, по прямому URL поста и вложенных изображений.
- **Then:** 404 всем, кроме автора/moderator/admin.
- **And:** Кэш не отдаёт прежнюю версию.

### TC-SOC-04 · Группа SC-SOC-04 «Удаление поста с медиа»

#### TC-SOC-04a · Удаление или правка чужого поста → 403 (IDOR)
- **Уровень:** API · **Связи:** SC-SOC-04; AC-24; NFR-SEC-06 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** Пост F-MEM; F-USER2.
- **When:** F-USER2 удаляет/правит пост по ID.
- **Then:** 403.
- **And:** Пост и вложения без изменений.

#### TC-SOC-04b · Удаление своего поста: пост и вложения исчезают
- **Уровень:** E2E Playwright · **Связи:** SC-SOC-04; AC-24; OD-40 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** Пост F-MEM с двумя изображениями.
- **When:** Автор удаляет пост.
- **Then:** Мягкое удаление; пост и вложения исчезают из ленты, галереи и поиска; ссылки показывают «Материал удалён».
- **And:** Запись в `audit_log` сохраняется (политика хранения).

#### TC-SOC-04c · Прямой URL удалённого изображения → 404
- **Уровень:** API · **Связи:** SC-SOC-04; AC-24; NFR-SEC-13 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** Удалённый пост с изображением.
- **When:** Запрос прямого URL файла и подписанной ссылки после удаления.
- **Then:** 404; файл не отдаётся.
- **And:** Кэш/CDN не отдают прежнюю версию.

#### TC-SOC-04d · Изображение, прикреплённое к другому объекту, не удаляется
- **Уровень:** API · **Связи:** SC-SOC-04, SC-GAL-02; AC-24 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** Изображение прикреплено к посту и к метке (`media_attachments`).
- **When:** Удаляется пост.
- **Then:** Связь с постом снята; изображение остаётся для метки.
- **And:** Физическое удаление только когда ссылок не осталось.

#### TC-SOC-04e · Физическая очистка файлов через 30 дней
- **Уровень:** API (управляемые часы, фоновая задача) · **Связи:** SC-SOC-04; AC-24; OD-40; NFR-PERF-09 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** Мягко удалённый пост с файлами.
- **When:** Проходит 30 дней и запускается задача очистки (дважды).
- **Then:** Файлы удалены из Storage; повторный запуск не выполняет действие дважды; записи аудита сохранены.
- **And:** Квота пользователя уменьшена.

### TC-SOC-05 · Группа SC-SOC-05 «Недопустимый файл»

#### TC-SOC-05a · Доступ к `media` по ролям (RLS)
- **Уровень:** API (SQL/REST) · **Связи:** SC-SOC-05; AC-08, AC-12; NFR-SEC-13; T-UPLOAD · **Приоритет:** Blocker · **Релиз:** P1a
- **Given:** Файлы `public`, `guild`, `private`.
- **When:** Запросы ролей `anon`, `authenticated`, owner, moderator, admin к `media` и URL файлов.
- **Then:** Результат соответствует матрице: `anon` — только `public`, закрытое — 404.
- **And:** Файлы не лежат в веб-корне.

#### TC-SOC-05b · SVG, HTML или исполняемый файл под расширением изображения — отказ
- **Уровень:** API · **Связи:** SC-SOC-05; AC-08; NFR-LIM-10, NFR-LIM-11; T-XSS, T-UPLOAD · **Приоритет:** Blocker · **Релиз:** P1a
- **Given:** Файлы SVG, HTML, EXE, polyglot (картинка+скрипт) с расширением `.png`.
- **When:** Загружаются.
- **Then:** Отказ по проверке типа по содержимому; допустимы только JPEG/PNG/WebP.
- **And:** Файл не сохранён; попытка в `security_events`.

#### TC-SOC-05c · Файл >10 МБ или >4096 px — отказ
- **Уровень:** API · **Связи:** SC-SOC-05; NFR-LIM-08, NFR-LIM-09; T-SSRF (P2) · **Приоритет:** Major · **Релиз:** P1a
- **Given:** Изображения 10 МБ+1 Б и 4097 px.
- **When:** Загружаются.
- **Then:** 413/422 с понятной причиной.
- **And:** Загрузка по URL (ImageFrame) — P2: SSRF-контроль allowlist схем/хостов, без редиректов и приватных IP проверяется в P2.

#### TC-SOC-05d · EXIF/GPS удалены, формат — WebP
- **Уровень:** API · **Связи:** SC-SOC-05; AC-08; NFR-LIM-11; T-XSS · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** JPEG с EXIF/GPS.
- **When:** Загружается и скачивается.
- **Then:** Сохранённый файл — WebP без EXIF/GPS.
- **And:** Названия файлов санитизированы.

#### TC-SOC-05e · Квота 500 МБ, 20 загрузок в час, 50 МБ в сутки — 429/413
- **Уровень:** API · **Связи:** SC-SOC-05; NFR-LIM-06, NFR-LIM-07; T-UPLOAD · **Приоритет:** Major · **Релиз:** P1a
- **Given:** Пользователь у границ лимитов.
- **When:** Превышает каждый лимит.
- **Then:** 429 (частота/суточный объём) либо 413 (квота) с временем до разблокировки.
- **And:** Лимиты не обходятся несколькими сессиями.

### TC-SOC-06 · Группа SC-SOC-06 «Видимость для guest и applicant»

#### TC-SOC-06a · Гость читает ленту: видны только официальные новости и public-галерея

- **And:** Скрытые материалы не присутствуют в HTML/JSON.

#### TC-SOC-06b · `applicant` читает ленту, но не публикует

- **Then:** Чтение доступно; публикация — 403 и кнопки нет.

#### TC-SOC-06c · `restricted` видит только `public`
- **Уровень:** API · **Связи:** SC-SOC-06; OD-02 · **Приоритет:** Major · **Релиз:** P1a
- **Given:** F-RESTR.
- **When:** Читает ленту.
- **Then:** Только `public`; публикация и реакции закрыты.
- **And:** Гильдейский контент недоступен.

#### TC-SOC-06d · Гость вызывает API ленты и получает только разрешённые типы
- **Уровень:** API · **Связи:** SC-SOC-06; OD-02 · **Приоритет:** Critical · **Релиз:** P1a
- **Given:** F-GUEST.
- **When:** Прямые запросы API ленты с различными фильтрами и ID.
- **Then:** В выдаче только официальные новости/public; запрос по ID закрытого — 404.
- **And:** Нет различий в поведении «нет прав» и «нет объекта» (не раскрываем существование).

#### TC-SOC-07d · Повтор идентичного текста подряд отклоняется

#### TC-SOC-07e · UI показывает время до разблокировки
- **Уровень:** E2E Playwright · **Связи:** SC-SOC-07; NFR-LIM-04 · **Приоритет:** Minor · **Релиз:** P1a
- **Given:** Лимит исчерпан.
- **When:** Открывает форму поста.
- **Then:** Показан обратный отсчёт/время до разблокировки; кнопка отправки отключена.
- **And:** Доступно с клавиатуры и экранных читалок (NFR-A11Y).

### 3.10. P1b — Опросы (POLL)

- **Уровень:** API · **Связи:** SC-POLL-01; AC-31 (смежно); OD-27 · **Приоритет:** Critical · **Релиз:** P1b

### TC-POLL-02 · Группа SC-POLL-02 «Повторный голос, двойной клик, гонка»

#### TC-POLL-02a · Голос от гостя → 401/403
- **Уровень:** API · **Связи:** SC-POLL-02; AC-09; T-RACE · **Приоритет:** Critical · **Релиз:** P1b
- **Given:** Открытый опрос; F-GUEST.
- **When:** Голосует.
- **Then:** 401/403.
- **And:** Голос не записан.

#### TC-POLL-02b · Повторный голос через API, двойной клик, гонка — один голос
- **Уровень:** API (параллельно) + E2E Playwright · **Связи:** SC-POLL-02; AC-09; T-RACE · **Приоритет:** Blocker · **Релиз:** P1b
- **Given:** F-MEM, опрос с одиночным выбором.
- **When:** 20 параллельных запросов голоса; двойной клик в UI; повтор после ответа.
- **Then:** Ровно один голос записан, остальные 409.

Перечень повторяет [роли и права, §7](../01-product/03-roles-permissions.md#7-обязательные-негативные-проверки-будущие-tc): ID не перенумерованы, определения (Given / When / Then) — в разделе 3. Правило всех строк: проверка выполняется **двумя способами** — через UI (кнопка/пункт отсутствует либо действие отклонено) и **обходом UI** (прямой вызов API/URL), а ожидание то же; скрытие кнопки не считается защитой. Для чужого закрытого объекта сервер отвечает 404 (не раскрывает существование), для запрета действия над видимым объектом — 403. Каждый отказ пишется в `security_events` (`authz.denied`) [ПРЕДЛОЖЕНИЕ КОМАНДЫ].
